# AI Календарь — интерфейс

Мобильный интерфейс AI-календаря по мотивам видео-референса: календарь, день по слоям «Утро / День / Вечер» и чат с ассистентом: LLM отвечает стримом, а через инструменты смотрит расписание, ищет свободное окно и добавляет события в календарь.

Приложение многопользовательское: регистрация и вход по логину и паролю, данные каждого привязаны к его аккаунту, задачи можно делить с другими — по `@логину` в названии или через список участников; события и чат остаются личными.

Можно подключить внешние календари — Google, Outlook, Яндекс, iCloud, Nextcloud или любую ссылку `.ics`: их события появляются рядом со своими, ассистент учитывает их при поиске времени, а новые события и правки уходят обратно в выбранный календарь. И наоборот — личная ссылка `.ics` показывает события приложения в Google, Apple или Outlook (см. «Внешние календари»).

Фронтенд — PWA на React; бэкенд — Go (`server/`); собираются в один Docker-образ. Ассистент — LLM с function calling (OpenAI-совместимый API, SSE-стриминг); события и история чата хранятся на сервере.

## Запуск

### Docker (UI + бэкенд в одном контейнере)

```bash
docker compose up --build        # http://localhost:8080
# или
docker build -t ai-calendar .
docker run -p 8080:8080 -v ai-calendar-data:/data ai-calendar
```

Образ собирается в три стадии: Node собирает PWA, Go встраивает её в бинарник через `go:embed`, итоговый образ — distroless, около 17 МБ. Есть `HEALTHCHECK`, сервер работает от непривилегированного пользователя.

`docker compose up --build` поднимает два сервиса: приложение и PostgreSQL 17 (образ `postgres:17-alpine`). Данные лежат в томе `db-data`; старый `data.json` из тома `data` при первом запуске импортируется в базу однократно. Пароль базы задаётся `DB_PASSWORD` (по умолчанию `calendar`).

| Переменная     | По умолчанию                   | Назначение                                                                         |
| -------------- | ------------------------------ | ---------------------------------------------------------------------------------- |
| `PORT`         | `8080`                         | Порт HTTP                                                                          |
| `DATABASE_URL` | —                              | Подключение к PostgreSQL; если задано — данные в БД, иначе в JSON-файле            |
| `DATA_DIR`     | `/data`                        | Каталог с `data.json`; пустое значение — хранить в памяти; с БД — источник импорта |
| `LLM_API_KEY`  | —                              | Ключ OpenAI-совместимого API; без него чат отвечает заглушкой                      |
| `LLM_BASE_URL` | `https://api.neuraldeep.ru/v1` | Адрес API модели                                                                   |
| `LLM_MODEL`    | `qwen3.6-unlim-noreason`       | Модель ассистента                                                                  |
| `STATIC_DIR`   | —                              | Раздавать UI с диска вместо встроенного (для разработки)                           |

### Деплой на сервер

Продакшен-копия живёт на домашнем сервере `192.168.0.16` (SSH: `root`, ключ `~/.ssh/id_ed25519`), проект — в `/opt/ai-calendar`, UI — на `http://192.168.0.16:8090`. Обновление:

```bash
# исходники → сервер (.env сервера не трогаем: там LLM_API_KEY и APP_PORT)
rsync -az --delete \
  --exclude node_modules --exclude .git --exclude .github --exclude .env \
  --exclude dist --exclude dist-single --exclude server/data \
  --exclude server/web/dist --exclude '*.log' \
  ./ root@192.168.0.16:/opt/ai-calendar/

ssh root@192.168.0.16 'cd /opt/ai-calendar && docker compose up -d --build'

# проверка
curl http://192.168.0.16:8090/api/health
TOK=$(curl -s -X POST http://192.168.0.16:8090/api/auth/login -H 'Content-Type: application/json' \
  -d '{"username":"...","password":"..."}' | jq -r .token)
curl -N -X POST http://192.168.0.16:8090/api/chat -H "Authorization: Bearer $TOK" \
  -H 'Content-Type: application/json' -d '{"text":"привет"}'
```

Нюансы: порт хоста задаёт `APP_PORT` в `.env` — там `8090`, потому что `8080` занят llama.cpp; данные — в PostgreSQL (`db-data`), пересборка их не трогает; `--delete` убирает удалённые из репозитория файлы, исключённые пути сохраняются.

### Разработка

```bash
npm install
make api          # Go-сервер на :8080 (нужен Go 1.24+)
npm run dev       # UI на :5173, /api проксируется на :8080
```

Без запущенного сервера UI работает в **локальном режиме**: демо-данные и всё, что вы создали, хранятся в браузере (`localStorage`) — аккаунт там не нужен. Режим выбирается при запуске сам: если `/api/health` отвечает — данные с сервера и приложение просит войти; токен сессии хранится в браузере, уходит в каждом запросе и сбрасывается по `401`. Если приложение уже работало с сервером и сеть пропала, оно остаётся в режиме сервера и показывает кэш, а правки событий и задач ждут в офлайн-очереди (см. раздел PWA). Явно: `VITE_API_MODE=local|server`, адрес бэкенда на другом домене — `VITE_API_URL`.

Сборка без Docker:

```bash
npm run build        # dist/ — PWA для хостинга (на GitHub Pages работает в локальном режиме)
npm run build:single # dist-single/index.html — всё в одном файле, без service worker
make web             # положить сборку в server/web/dist, затем: cd server && go build ./cmd/server
```

Workflow `.github/workflows/deploy.yml` публикует статическую версию при пуше в `main`. Включите Pages: **Settings → Pages → Source: GitHub Actions**.

## Бэкенд (Go)

Только стандартная библиотека Go: `net/http` с маршрутами Go 1.22, `log/slog`, `embed`; для PostgreSQL — `pgx/v5`. Хранилище изолировано интерфейсом в `internal/store`: по умолчанию JSON-файл с атомарной записью, при заданном `DATABASE_URL` — PostgreSQL (таблицы `users`, `sessions`, `events`, `messages`, `tasks`, `task_members`, `notifications` создаются миграцией, старый `data.json` импортируется однократно).

**Аккаунты и сессии.** Регистрация и вход по логину (латиница, `@логин`) и паролю; пароль хранится как PBKDF2-SHA256-хэш (stdlib `crypto/pbkdf2`), сессия — Bearer-токен сроком 30 дней со скользящим продлением, в базе лежит его sha256. Все маршруты данных требуют `Authorization: Bearer <token>`; пользователь попадает в контекст запроса через middleware, и хранилище фильтрует записи по нему. Данные до-аккаунтной эпохи (без владельца) усыновляет первый зарегистрированный пользователь.

**Совместные задачи.** Задачу видят владелец и участники (`task_members`), обе стороны могут править поля. Поделиться можно двумя способами: `@логин` в названии или заметке (парсится сервером при создании и правке) и явный список `members` / маршрут участников. Участник получает уведомление, может выйти сам; владелец удаляет задачу у всех и снимает любых участников. События и история чата — всегда личные.

Как работают упоминания:

- Задачу делит только **новое** упоминание — которого не было в тексте до правки. Повторные сохранения не шлют уведомления снова, а того, кто вышел или кого убрал владелец, старое упоминание обратно не возвращает. Стёрли `@логин` и написали заново — это новое приглашение.
- Упоминание начинается после пробела, начала строки или знака препинания: в «misha@bob.ru» и «иван@bob» упоминания нет. Точка, дефис или подчёркивание в конце («с @bob.») к логину не относятся, если такого логина нет.
- Неизвестный `@логин` — просто текст. Упомянуть себя или владельца можно: участником они не становятся и ошибки нет. Явно добавить владельца через `members` — ошибка 400.
- У упомянутого общая задача появляется без перезагрузки: приложение раз в минуту проверяет уведомления и при новом перечитывает задачи.

| Метод и путь                                      | Что делает                                                                                          |
| ------------------------------------------------- | --------------------------------------------------------------------------------------------------- |
| `GET /api/health`                                 | Проверка живости и версия                                                                           |
| `POST /api/auth/register`                         | Аккаунт: `{username, password, name?}` → `{token, user}`; логин уникален без учёта регистра         |
| `POST /api/auth/login`                            | Вход → `{token, user}`                                                                              |
| `POST /api/auth/logout`                           | Завершить сессию (токен сгорает)                                                                    |
| `GET /api/me` · `PATCH /api/me`                   | Профиль; правка `{name}`                                                                            |
| `GET /api/users?q=`                               | Поиск пользователей для шаринга (без себя); пустой `q` — все                                        |
| `GET /api/notifications`                          | Уведомления (о шаринге задач), последние 100                                                        |
| `POST /api/notifications/read`                    | Отметить все прочитанными                                                                           |
| `GET /api/events?date=2026-10-20`                 | События дня пользователя                                                                            |
| `POST /api/events`                                | Новое событие `{date, title, subtitle?, start, end, badge?}` (минуты от 0:00)                       |

| `DELETE /api/events/{id}`                         | Удалить событие                                                                                     |
| `GET /api/month?year=&month=`                     | Значки событий по дням месяца (месяц с 1)                                                           |
| `GET/POST /api/tasks`                             | Задачи и цели: `{title, subtitle?, kind?, category?, due?, members?}` — `members` добавляет логинов |

| `GET/POST /api/messages`                          | История чата с ассистентом (клиент пишет только реплики `user`)                                     |
| `POST /api/chat`                                  | Диалог с ассистентом: `{text}` → SSE-стрим `delta`/`tool`/`error`/`done`; реплики сохраняются       |
| `GET /api/integrations`                           | Подключённые календари и какие OAuth-сервисы включены (`providers`)                                 |
| `POST /api/integrations/caldav/discover`          | Календари на CalDAV-сервере: `{url, username, password}` → `{calendars}`                            |
| `POST /api/integrations`                          | Подключить `{kind: ics\|caldav, url, name?, badge?, username?, password?, writable?, primary?}`     |
| `PATCH /api/integrations/{id}`                    | `{name?, badge?, primary?}`; `primary` — сюда уходят новые события                                  |
| `DELETE /api/integrations/{id}`                   | Отключить календарь (его события пропадают из приложения)                                           |
| `POST /api/integrations/{id}/sync`                | Синхронизировать сейчас; ошибка сервиса — в `lastError`                                             |
| `POST /api/integrations/oauth/{provider}/start`   | `google` / `outlook` → `{url}` страницы входа                                                       |
| `GET /api/integrations/oauth/{provider}/callback` | Возврат со страницы входа (публичный, пользователь — из подписанного `state`)                       |
| `GET/POST/DELETE /api/feed`                       | Личная лента `.ics`: путь, новая ссылка (старая перестаёт работать), выключить                      |
| `GET /api/feed/{token}.ics`                       | Сама лента для Google/Apple/Outlook (публичная, доступ — по секрету в ссылке)                       |

Ошибки — JSON `{"error": "понятный текст"}` с кодом 400/401/403/404/409/413/424/429 (424 — внешний календарь не принял изменение, 429 — превышен лимит, в ответе `Retry-After`). Лимиты: вход — 10 попыток в один аккаунт (дальше одна в 30 с) и 30 с одного адреса, регистрация — 20 с адреса, чат — 10 сообщений подряд (дальше одно в 6 с); одновременных PBKDF2 — не больше четырёх. Тело запроса ограничено 64 КБ, неизвестные поля отклоняются. Название — до 120 символов, подзаголовок — до 200, сообщение — до 2000 (в локальном режиме те же ограничения). Если запись `data.json` не удалась, изменение откатывается. Сервер отдаёт `Content-Security-Policy` (всё своё, картинки — по HTTPS). Всё, что не `/api/*`, — PWA: файлы с хешем кэшируются навсегда, `index.html`, `sw.js` и манифест — `no-cache`, неизвестные пути отдают `index.html`.

Ассистент — цикл инструментов поверх чат-комплита: модель может вызвать `get_day_schedule`, `find_free_slots`, `create_event`, `update_event`, `delete_event`, `list_tasks`, `create_task`, `update_task`, `delete_task`, а для совместной работы — `list_users` (логины пользователей) и параметр `members` в задачных инструментах. Удаление подтверждает сервер, а не только промпт: первый вызов `delete_event`/`delete_task` ничего не удаляет и возвращает `needs_confirmation`, удаление проходит только при повторном вызове в следующем ходе диалога, после реплики пользователя (в течение 10 минут). Так команда «удали» в тексте чужого события не сработает за один ход. Тексты событий и задач промпт велит считать данными, а не указаниями. В промпте — дата и время в поясе пользователя; `find_free_slots` на сегодня не предлагает прошедшее время. Последний из шести заходов идёт без инструментов, чтобы модель ответила текстом. Ответ стримится по токенам, параллельные вызовы инструментов собираются по `index`; если провайдер не принял `stream` (400/404/422…), запрос повторяется обычным, а 401/429/5xx не повторяются. Если модель оборвалась посреди ответа, начало сохраняется в истории, а поток шлёт `error`.

Блок «Задачи и цели» на главном хранится в таблице `tasks` (в Postgres — создаётся миграцией). Цели (`kind=goal`) показываются большими карточками с отметкой и дедлайном, задачи (`kind=task`) — строками с сегментом категории и чекбоксом; общие задачи помечаются аватарками участников.

## Внешние календари

Шторка «Календари» открывается из аккаунта (аватар на главном). Всё работает только в режиме сервера.

| Как подключить                 | Направление   | Что нужно                                                                                   |
| ------------------------------ | ------------- | ------------------------------------------------------------------------------------------- |
| **Google Календарь**           | в обе         | Кнопка «Google Календарь» — вход через Google (нужно OAuth-приложение на сервере, см. ниже) |
| **Outlook / Microsoft 365**    | в обе         | Кнопка «Outlook» — вход через Microsoft (OAuth-приложение на сервере)                       |
| **Яндекс, iCloud, Nextcloud…** | в обе         | CalDAV: логин и **пароль приложения** (Яндекс ID → Безопасность; account.apple.com)         |
| **Любая ссылка `.ics`**        | только чтение | Праздники, расписание команды, «Секретный адрес в формате iCal» из Google без OAuth         |
| **Наш календарь в других**     | наружу        | «Создать ссылку» → вставить в Google («Другие календари» → «По URL»), Apple или Outlook     |

Как это устроено:

- События внешних календарей хранятся вместе со своими (`source` — id подключения), поэтому день, месяц, «Далее» и инструменты ассистента (`get_day_schedule`, `find_free_slots`) видят их без отдельной логики. События на весь день показываются полосой над шкалой и время не занимают.
- Синхронизация — окно «−30 … +365 дней» вокруг сегодня: при подключении, по кнопке «Обновить» и в фоне раз в `CALENDAR_SYNC_INTERVAL`. Повторы (`RRULE`, `EXDATE`, перенесённые и отменённые вхождения) разворачиваются на сервере; Google и Microsoft разворачивают их сами.
- Календарь с отметкой «Новые события — сюда» получает события, созданные в приложении и ассистентом. Правки и удаления событий из Google/Outlook/CalDAV сначала уходят туда (CalDAV — с проверкой версии `If-Match`, чужие свойства вроде напоминаний сохраняются). Если сервис недоступен, новое событие сохраняется в приложении, а ошибка видна в настройках календаря.
- Только для чтения: подписки `.ics`, вхождения повторяющихся серий CalDAV, события на весь день и многодневные (они режутся по дням).
- Время переводится в пояс пользователя: браузер сам сообщает его серверу (`PATCH /api/me {timeZone}`).
- Пароли CalDAV и OAuth-токены хранятся зашифрованными (AES-256-GCM, ключ `SECRET_KEY` или `DATA_DIR/secret.key`). Смена ключа — календари с паролем придётся подключить заново.
- Сервер не ходит по адресам внутренней сети (loopback, 10/8, 192.168/16 и т. п.) — пользователь вводит адреса сам. Свой Nextcloud дома — `CALENDAR_ALLOW_PRIVATE=1`.

**Google.** В [Google Cloud Console](https://console.cloud.google.com/) создайте проект, включите Google Calendar API, на странице OAuth consent screen добавьте область `…/auth/calendar.events`, затем Credentials → OAuth client ID → Web application с адресом возврата `PUBLIC_URL/api/integrations/oauth/google/callback`. Google требует HTTPS-домен (кроме `localhost`), поэтому на сервере по IP-адресу вход через Google не заработает — там используйте ссылку `.ics`. Пока приложение в режиме «Testing», войти могут только добавленные тестовые пользователи, а доступ живёт 7 дней.

**Microsoft.** В [Entra ID → App registrations](https://entra.microsoft.com/) зарегистрируйте приложение для «любых учётных записей Microsoft», платформа Web с адресом возврата `PUBLIC_URL/api/integrations/oauth/outlook/callback`, разрешения Microsoft Graph `Calendars.ReadWrite` и `offline_access`, создайте секрет клиента.

## PWA

- **Установка:** манифест с иконками (в том числе maskable), `standalone`, тема и фон без белой вспышки. На Android и в десктопном Chrome — кнопка «Установить» на главном экране, на iPhone — подсказка «Поделиться → На экран „Домой“».
- **Офлайн:** собственный service worker (`src/sw.ts`, Workbox-модули через `injectManifest`) кэширует оболочку приложения и шрифты. Ответы API сохраняются по схеме «сначала сеть, потом кэш», фото — «сначала кэш». Без сети показывается плашка со счётчиком ожидающих изменений, а данные берутся из кэша.
- **Очередь изменений:** мутации событий и задач при обрыве сети складываются в `outbox` (IndexedDB: операции, карта временных id → серверных, метаданные) и поверх чтений показываются как уже применённые — офлайн-созданное переживает перезапуск. Очередь доигрывается по Background Sync даже с закрытым приложением (Chromium/Android); где Sync API нет (Safari, Firefox), её выгоняет страница — на старте, по событию `online` и по таймеру. Повторные правки одной сущности сливаются, удаление неотправленного create отменяет его (правка или удаление во время отправки create встают следом отдельной операцией). Очередь помнит владельца: вход другого пользователя стирает чужие операции, а выход и повторный вход того же — нет. Кэш ответов API в service worker общий для аккаунтов, поэтому при выходе и смене пользователя он стирается. Чат-стрим в очередь не кладётся — у него свой UI ошибки и повтора.
- **Авторизация офлайн:** токен сессии дублируется из `localStorage` в метаданные очереди — у service worker нет доступа к `localStorage`, а replay идёт с `Authorization: Bearer`. Ответ `401` останавливает обход, не теряя операций, — до свежего входа.
- **Обновления:** о новой версии сообщает уведомление «Обновить», перезагрузка — только по нажатию. Приложение проверяет обновления раз в час.
- **Быстрые действия** с иконки: «Новое событие», «Ассистент», «Календарь на месяц» (`?action=…`).

## Стек

- **React 19 + TypeScript (strict, `noUncheckedIndexedAccess`) + Vite**;
- **framer-motion** — переходы экранов, layout-анимации, жесты; бесконечные анимации отключаются при «уменьшении движения»;
- **CSS Modules** и токены в `src/styles/global.css` (цвета, радиусы, тени, слои z-index);
- шрифт **Inter Variable** подключён локально, с кириллицей.

## Проверки

```bash
npm run typecheck   # tsc для приложения и конфигов
npm run lint        # ESLint: typescript-eslint, react-hooks (правила React Compiler), jsx-a11y
npm run test        # vitest: доменная логика, даты, склонения, API-клиенты, офлайн-очередь
npm run check       # всё вместе + prettier --check

cd server && gofmt -l . && go vet ./... && go test -race ./...
# хранилище на настоящем PostgreSQL (нужна пустая тестовая база):
TEST_DATABASE_URL=postgres://... go test ./internal/store -run TestPostgres
```

Внешние сервисы в тестах не нужны: CalDAV, Google и Microsoft подменяются поддельными серверами из `server/internal/calsync/fakecal`.

Те же проверки и сборка Docker запускаются в CI (`.github/workflows/ci.yml`) на каждый пуш и PR.
